# webapp subsystem details

Overflow from `packages/webapp/CLAUDE.md`. Each section is the deep reference for a subsystem enumerated there.

## Kernel Host

- Path: `packages/webapp/src/kernel/`
- `host.ts` — `createKernelHost(config)` factory: single boot sequence for every float (orchestrator, lick-manager, agent-bridge, tray subs, cone bootstrap, BshWatchdog, `/proc` mount). `node-rest` opens the `/licks-ws` bridge; extension-delegate leaders route licks through the tray worker. Float discriminator: `resolveFloatTopology()` in `shell/float-topology.ts` (`core/float-topology.ts` is a compatibility re-export). `kernel-worker.ts` is the DedicatedWorker entry.
- `process-manager.ts` tracks every long-running async unit; pids uint32 from 1024+; `signal(pid, sig)` honors SIGINT/SIGTERM/SIGKILL/SIGSTOP/SIGCONT. `proc-mount.ts` serves read-only `/proc` (`cat /proc/<pid>/{status,cmdline,cwd,stat}`).
- `realm/` hard-killable runner. `runInRealm()` spawns per-task `DedicatedWorker`; SIGKILL → exit 137. JS runs in kernel worker via `createJsWorkerRealm()`; `realm-host` proxies `vfs`/`exec`/`fetch`. Node shims in `realm/helpers/` (barrel: `js-realm-helpers.ts`). Sync-XHR bridge (`readFileSync`/`writeFileSync`, `child_process.execSync`/`execFileSync`/`spawnSync`) via `realm/sync-{xhr,fs-*,exec-*}.ts` + `ui/sync-fs-sw-handler.ts` with per-realm capability tokens.
- `facade.ts` holds a `request-scoop-messages` for a cone whose `cone-create` is still in flight (`conesBeingCreated`, #2840). `registerScoop` is what LISTS the new cone to the page, and the rail selects a cone the instant its real record lands, so the replay request routinely arrives before the brief has been buffered. Answering there is not a dropped request but a WRONG one: every source is legitimately empty and the panel wholesale-replaces the thread with nothing. The client's 5 s recovery only re-asks a genuinely unanswered snapshot (#2859), so an empty replace would stay empty — the gate is the only thing that waits. It opens on the brief being BUFFERED, never on the turn finishing — waiting for the model would leave the previous cone's transcript on screen for the length of the first turn.
- Deep reference: `docs/kernel/process-model.md`.

## Computers

- Path: `packages/webapp/src/computers/`. Unranked in the layer stack (shell/kernel/cdp may import it; `computers` → `ui` is a back-edge — the store lives in `ui/`).
- Protocol types: `@slicc/shared-ts` (`computer-protocol.ts`). Deep reference: `docs/computer-protocol.md`.
- `registry.ts` / `host.ts` — kernel registry (`ProcessKind 'computer'`) and `computers` / `computer-frame` / `computer-watch` / `computer-unwatch` / `computer-input` pump. Lazy-loaded from `kernel-worker.ts`.
- Adapters: `v86.ts` (adopt VM pid; `close()` detaches only), `tab.ts` (Local vs Bridged; refuses SLICC app tabs), `jsh.ts` (`sliccy:computer` via `kernel/realm/realm-computer-bridge.ts`, including `subscribe`/`frame`/`unsubscribe`).
- Shell: `shell/supplemental-commands/computer/` (xdotool + Anthropic aliases). Frozen frames: `$TMPDIR/computer/<name>/<seq>.jpg`.
- Page store: `ui/computers-store.ts`. Refcounted `watch`/`unwatch` so overlay, a live bash row, the lightbox, and tray followers share one kernel subscription. Each subscriber keeps its own fps/maxWidth; the kernel receives the max of the live set and is re-sent when that max changes. `recordInvocation` / `newestInvocation` drive the newest-call live vs frozen rule. `input()` forwards overlay `computer-softkey` events and lightbox HITL as `computer-input`.
- Overlay + lightbox: `ui/wc/wc-computers.ts`, installed lazily from `wc-live.ts`. `mergeOverlayTabs` puts browser tabs first, then every registered computer as `id: computer:<id>` (heading "Browser · tabs & computers"). A failed CDP `listAllTargets` still paints those computer cards (`mergeOverlayTabs([])` in `wc-browser.ts`) instead of wiping the overlay. `wc-browser.ts` MUST skip `parseComputerOverlayId` before the follower-teleport `id.includes(':')` path — a computer id contains `:`. Opening the overlay watches every registered computer at 2 fps / 480 px so cards fill from `computer-frame` pushes (not a prior `computer watch` shell). Overlay activate/peek opens `<slicc-image-preview>` via `setSrc` / `isOpen`; lightbox watch on open (4 fps / 768 px), unwatch on close; no attach/foreground. Soft keys call `store.input()`. A live lightbox with `inputAllowed` sets `preview.drive` after a watched frame is on screen and maps displayed CSS pixels to native (`mapDisplayedToNative` + `keysymFromKeyEvent`) before `store.input()`; Escape/backdrop still close; frozen stills never get `drive`. Computer cards have no close control. `applyFrame` compact-copies bytes (offset views, JSON-cloned typed arrays); `frameToDataUrl` sniffs PNG/JPEG magic so a frozen `.jpg` path that holds PNG still renders. The example `MINIMAL_JPEG` SOF0 stub is not browser-decodable — overlay/row `<img>` needs a real JPEG/PNG payload.
- Bash rows: `bashBody` additionally sets `toolCallId` and `done` on `<slicc-bash-renderer-computer>`. The host resolves the target from `-c` / `--computer`, else a `target: <id>` stamp the shell prepends after `$COMPUTER` / last `use` / sole registered, and writes it to `computerId`. Newest live rows watch at 2 fps / 480 px; LIVE chrome only after a pushed frame is on screen. Frozen rows (older calls, or the newest call before the first push) read their own `screen: <path>` then their own `<img:>`, otherwise nothing — never the shared latest frame. Each async frozen-file load carries a generation token and applies only while the row is still bound, still frozen, and still on the same hint. Clicking a frozen still opens the lightbox even when no target id is available (static preview; no watch). Progress chrome stays `wcmsg-bash`.
- Tray: `scoops/tray-leader/computers-router.ts` (callbacks on `LeaderSyncManagerOptions.computers`, filled from the store in `page-leader-tray.ts` so scoops/ never imports ui/). Additive messages, protocol version stays 8. Caps 2 fps / 480 px when crossing the tray. Biscotto seats cannot send watch/unwatch/input or receive list/frames/native capture. iOS decodes `computers.list` / `computer.frame` / `computer.watch` / `computer.input` (viewer cards + soft keys); `computer.native.*` is the macOS capture path and iOS ignores it. Native input is a request/ack: the launcher always answers `computer.native.input` with `computer.native.input.result`, the leader awaits it through panel RPC, and the shell verb surfaces Accessibility denials.

## Orchestrator

- `orchestrator.ts` owns scoop lifecycle, routing, shared state, and pre-removal `onScoopUnregistered` snapshots. `scoop-context.ts` owns per-scoop prompt execution and FS/tool isolation — it is a ~620-line coordinator over `scoops/scoop-context/`, one module per reason to change (#2334): `runtime-init.ts` (boot sequence) · `turn-runner.ts` (attempt/retry) · `turn-process.ts` (the turn's pid + exit code) · `run-bounds.ts` (#1972 ceilings) · `agent-event-router.ts` + `agent-end-dispatch.ts` (event plumbing and what a terminal `agent_end` means) · `overflow-recovery.ts` / `image-recovery.ts` · `session-persistence.ts` (#1987) · `turn-journal.ts` (in-flight turn record; reload recovery in `scoops/interrupted-work-recovery.ts`, see `docs/work-unit.md`) · `bash-job-reaper.ts` (#1166) · `live-updates.ts` (hot-swaps onto a running agent) · `shell-and-skills.ts`, `tools.ts`, `agent-factory.ts`, `session-helpers.ts`, `system-prompt.ts`, `directory-structure.ts`, `memories.ts`, `sudo-wiring.ts` (assembly) · `model-resolution.ts`, `thinking-level.ts`, `shell-env.ts`, `error-classification.ts` (record-level, no agent needed) · `callbacks.ts` (the owner's contract). Each module's header states what it owns; add a responsibility as a new module, not a method on the facade. `agent-bridge.ts` exposes `globalThis.__slicc_agent` (defaults: writable `[cwd, /shared/, <scratch>/, /tmp/]`, visible `[/workspace/, invokingCwd]`; `--read-only` replaces).
- `scoop-message-router.ts`: licks use `SCOOP_QUEUE_DEBOUNCE_MS` (1 s) bounded by `SCOOP_QUEUE_MAX_COALESCE_MS` (3 s); pure-lick batches defer while `ScoopContext.isBusy` without queue/watermark loss; `SCOOP_DEFERRAL_STARVATION_MS` reports backpressure once after 5 min. User `web` bypasses the window (immediate/awaited, prevents deferral).
- `transcript-limits.ts` caps bridge/event transcripts at 64 KB — never canonical `agent-sessions` history or compaction input.

## VirtualFS

- Path: `packages/webapp/src/fs/`. `virtual-fs.ts` POSIX-like FS backed by OPFS (in-memory in Node tests). `restricted-fs.ts` path ACLs. `mount-commands.ts` parses `--source`/`--profile`/`--no-probe`; `path-utils.ts` normalization. `same-file-identity.ts` is the inode check `rename`/`copyFile` use so a case- or NFC-equal dest on hostfs is a no-op instead of an O_TRUNC of the only copy (#3107).
- `appendFile` uses ZenFS append under the database mutation lock, so same-realm writers sharing that backend do not lose concurrent appends or copy the old payload in the adapter. Realm async `fs.appendFile` is one `vfs.appendFile` RPC into that locked path (`realm-host` `dispatchVfs`); it must not reimplement append as a client-side exists/read/write (#3174). `appendFileSync` stays an in-process cache RMW (cannot interleave inside one realm). Mounted backends currently use a read/concatenate/write fallback under that lock: this serializes append calls sharing a database; other mounted mutations and external host/remote writers still need backend concurrency control. `chmod` and `utimes` flush local metadata to the sidecar before returning and notify watchers; mounts report `ENOSYS` when unsupported. RestrictedFS and SudoFS gate all three operations, including private process-substitution descriptors. Delegated metadata writes honor the outer sudo approval while retaining parent/leaf symlink-escape checks. Cross-realm cache coherence is not added by append locking. Shell stat results preserve modes and backend-scoped identity; hostfs identity includes bridge, device, and inode, so alias mounts agree and unrelated devices differ. Older bridges lacking `dev` cannot supply a safe transactional identity. Rename/copy same-file checks prefer the scoped identity, so unrelated backends with colliding numeric device/inode pairs remain distinct.
- `mount/` — `MountBackend` + `backend-local.ts` / `backend-s3.ts` / `backend-da.ts` and shared `RemoteMountCache` (TTL+ETag, IDB). Browser-naive signing: CLI → `/api/s3-sign-and-forward`, extension → SW. `mount-table-store.ts` / `mount-recovery.ts` persist and restore. See `docs/mounts.md`.
- Optional `opfsAsyncCache: false` skips the eager ZenFS content copy and uses async fallbacks. Defaults remain enabled; same-database initializers are serialized and explicit configuration conflicts fail with EBUSY. See [preload experiment and native harness](filesystem-preload.md).

## Shell

- `filesystem-budgets.ts` selects the filesystem/memory subset of just-bash's
  hardened limits for `isScoop() === true`, using the existing child-role wiring in
  `scoops/scoop-context/shell-and-skills.ts`. It does not select the full hardened
  preset, which also shortens execution time and command counts. Trusted embedding
  code can pass `executionLimits` overrides and the optional `executionLimitProfile`
  constructor option. Defaults are chosen at shell construction. The limits apply
  where upstream consumes `CommandContext.limits`; custom commands must opt in.
  `maxFileSystemBytes` only covers just-bash's own in-memory filesystem, so it is
  deliberately absent from the scoop defaults for our supplied VFS.

- Path: `packages/webapp/src/shell/`. `almost-bash-shell-headless.ts` is the just-bash runtime; `supplemental-commands/` built-ins live under `docs/shell-reference.md`. `script-catalog.ts` is the shared `.jsh`/`.bsh` discovery for the shell and `which`, cached per `$PATH` root set; the `FsWatcher` cache is bypassed only for root sets a mount overlaps (external changes there are invisible). `vfs-adapter.ts` bridges shell → VFS and forwards `canWrite` (duck-typed for `VirtualFS`/`RestrictedFS`).
- `typescript` v7 (native) runs checks/builds; `typescript-js` (JS v6) powers browser `tsc`/`tst`/`esm-transpile` because v7 has no browser/WASM API. `builtin-shadow-map.ts` is authoritative for `ipx`/`npx` → built-in redirects. Raw scans: `jsh-discovery.ts` / `bsh-discovery.ts`.

### Filesystem adapter

- The just-bash curl patch uses optional `readFileBytes` for multipart files (binary-read fallback). It encodes multipart headers and inline values as UTF-8 before composing the raw-byte body; `curl -F` must preserve all byte values alongside Unicode form fields.

- `VfsAdapter` honors just-bash's read/write/append encoding options: UTF-8 by default, explicit `binary`/`latin1` for byte-shaped strings, and `hex`/`base64` for encoded representations. `readFileBytes()` exposes the optional branded byte API. `Uint8Array` writes retain their view boundaries. Download-cache hits apply only to explicitly binary writes; they never override text encoding. Request-body provenance still preserves curl's original file bytes when UTF-8 decoding is lossy.

## Media commands (`ffmpeg` / `ffprobe`)

`shell/supplemental-commands/ffmpeg-command.ts` (registration stub; the body is `ffmpeg/run.ts`,
`import()`ed on first use like `ffprobe/run.ts`), `ffmpeg/` (staging, input blobs, both engines),
`ffmpeg-wasm.ts` (core loader).

- **Two cores, one pin.** `@ffmpeg/core` (single-threaded, the default) and `@ffmpeg/core-mt`
  (pthreads over SharedArrayBuffer) are ipk-installed by the user. The mt core is OPT-IN:
  `FFMPEG_CORE=mt` (`ffmpeg/engine.ts`) on a `crossOriginIsolated` runtime (the hosted leader via
  Document-Isolation-Policy). It is not the default because ffmpeg starts a demux thread per input
  when there are several, and emscripten proxies those threads' `pthread_create` to a main thread
  blocked in `exec` — every multi-input job deadlocks (verified live 2026-09-03: single-input x264 at
  8 threads fine; any two-input lavfi job hangs, two workers past the 32-worker pool; tracked in #2810). `ffmpeg/run.ts`
  refuses multi-input jobs on the mt core and injects `MT_THREAD_BUDGET` (`-threads 8`,
  `-filter_threads 2`) unless the caller set them, because ffmpeg's defaults (1.5 × cores encoder
  threads, one filter thread per core per graph) also exhaust the pool. The loader tracks which core
  booted (`loadedFfmpegCorePackage()`); the first command's preference decides for the session.
  Every not-installed message goes through `ffmpegCoreNotInstalledMessage(preferMt)`; `-version`
  prints the `core:` line via `describeFfmpegCore()`. The live canary `ffmpeg-wasm-live.test.ts`
  resolves BOTH real packages.
- **Inputs never enter the wasm heap.** Each invocation gets a `StageNames` (`ffmpeg/staging.ts`):
  one WORKERFS mount at `/__in<id>` over `Blob`s, torn down with `unmountStagedInputs`. The
  `Blob` comes from `readInputBlob()` (`ffmpeg/input-blob.ts`): the VFS's native `File`
  (`VirtualFS.getNativeFile` — OPFS root or FSA picker mount, lazy by slice) or, for backends
  without a handle, a `Blob` over one whole-file read. Names are relative (`__in3_k1/x.mp4`) so
  the concat demuxer's `safe` check still passes. The stage id also namespaces the MEMFS output
  (`__out<id>_<basename>`), so concurrent runs on the shared core cannot clobber each other.
- **Only the output is buffered** (MEMFS, then one read back into the VFS). A core fault
  recycles the instance (`recycleFfmpeg`) and cleanup must NOT re-enter the dead worker; the
  `faulted` flag guards every `unmount`/`deleteFile`.
- **mediabunny fast path** (`ffmpeg/bunny-translate.ts` → `bunny-run.ts`, `bunny-probe.ts`,
  `fast-path.ts`, `engine.ts`). `translateToMediabunny(parsed)` is pure: one real input, one
  output in a container mediabunny writes, and every option either maps onto a `Conversion`
  (`BunnyPlan`) or REJECTS with the option named — never a silent drop, because a wrong accept
  produces a file the agent did not ask for. `runViaMediabunny` distinguishes `declined`
  (pre-flight: unreadable container, a track mediabunny would drop on its own — fall back to
  wasm, which then reports ffmpeg's own error) from `failed` (mid-run — the command's exit
  code). `FFMPEG_ENGINE` (`auto` | `wasm` | `mediabunny`) is read from the shell env. mediabunny
  is reached only via `import()` from these modules, so it never rides the boot graph; Vite dev
  pre-bundles it (`optimizeDeps.include`). Output is still a `BufferTarget` (kernel-worker JS
  heap, not the wasm heap) — streaming it to disk needs a VFS write stream, which does not exist
  yet. Under Node/vitest PCM WAV round-trips for real (`bunny-run.test.ts`); WebCodecs codecs
  decline and fall back, which is the same path a browser without an encoder takes.
- `getNativeFile` is part of the VFS read surface: `RestrictedFS` gates it like `readFile`
  (answering `null`, the caller's fallback read raises the sandbox ENOENT), `sudo-fs` lists it in
  `READ_ASYNC`, and `VfsAdapter` exposes it beyond just-bash's `IFileSystem` for duck-typing.
  `VirtualFS.readFileRange` prefers that lazy `File` (then `File.slice`) for OPFS-backed and
  FSA-picker paths so a `/preview/*` `Range` on `/shared/*.mp4` does not whole-file-read first
  (#2857). Hostfs/S3/DA/AEM/memory backends still return `null` and fall back to read-and-slice.

## Git

- **Line diffs use linear memory** (`git/diff.ts`). Unified diffs, `--stat`, and `merge-file` share an exact Myers search with two reusable `Int32Array` frontiers and an explicit stack of input ranges. Trim equal prefixes/suffixes before searching; never retain a frontier snapshot for each edit distance. The old trace exhausted the kernel worker heap on a 14,942-line versus 19,988-line comparison (7,724 snapshots of 69,861 numbers: roughly 540 million retained entries). High edit distances still cost CPU time, but scratch storage stays O(N+M), and merge alignment stays exact. `tests/git/myers-diff.test.ts` checks shortest paths against an independent oracle and runs those input sizes in a separate process with a 64 MiB heap.
- Path: `packages/webapp/src/git/`; one module per subcommand under `commands/`, dispatched by `git-commands.ts`. isomorphic-git runs over `vfs-fs-adapter.ts`, so **every object read is a VFS read** — and over a `--mount`ed host repo (`docs/mounts.md`) that is an HTTP round trip through the hostfs bridge. Cost is measured in reads, not in CPU.
- **A history walk must be bounded before it starts, never after** (#2714). `log -- <path>` used to materialize every commit on the branch, tree-diff each one through a `Promise.all` fan-out of two-tree `git.walk`s, and only then apply `-n`; on a 9.5k-commit repo that was ~25,500 bridge requests and a crashed renderer. `commands/log.ts` now hands a single-ref pathspec straight to `git.log({ filepath, depth, force: true })`, whose own walk resolves the path component-wise per commit tree and stops at `depth` matches. The forms that cannot use it (`--all`, `a..b`) filter the already-materialized list SEQUENTIALLY and break at the limit — never fan thousands of tree reads into the six-connection browser queue at once.
- **One read cache per command, never across commands** (#2709). isomorphic-git asks the same question once per walked file: `GitIndexManager.acquire` → `isIndexStale` `lstat`s `.git/index` on every `oid()` call, and `GitIgnoreManager.isIgnored` re-reads `.git/info/exclude` plus every ancestor `.gitignore` for every untracked candidate — 10,513 index stats and ~3,500 duplicate `.gitignore` reads in one warm `ls-files` over a mounted 3,549-file repo. `fs-command-cache.ts` memoizes `stat`/`lstat`/`readFile`/`readdir`, and **the memo IS the wrapper**: `execute()` builds a fresh `createCommandScopedReadCache` per invocation and threads it through `GitCommandContext`, so the memo dies with the command and two commands overlapping in time never share one. Never make it instance state — a `GitCommands` instance serves concurrent `execute()` calls, so a shared (even reference-counted) memo hands a second command the first one's stale reads. It caches an `ENOENT` (that is the answer) but never an `EIO` (that is a bridge hiccup, #2720); it never caches packfiles or pack indexes (isomorphic-git's own object cache owns those) or anything over 1 MB; **every entry, negative ones included, counts against one 50 k-entry cap** so a walk probing thousands of absent loose objects cannot grow it without bound; and it invalidates the path, its parent listing and the parent's stats on every write it sees. Because it only sees writes made through the adapter, `CACHEABLE_COMMANDS` in `git-commands.ts` is an **allowlist** — a subcommand that writes straight to `ctx.fs` (checkout, reset, rm, mv, stash, rebase, revert, clean, merge-file, config) gets the plain adapter instead. The read cache is the OUTER of two per-invocation memos: `contextFor()` wraps it around an adapter that already carries the `.git/objects` memo below (#2712, next bullets), so a read it misses still reaches the fan-out shortcut rather than the filesystem.
- **One `git` invocation = one view of `.git/objects`** (#2712). `createIsomorphicGitFs(vfs, { objectCache: true })` memoizes the `objects/pack` listing isomorphic-git re-reads on every packed object lookup, plus the `objects/` fan-out listing that decides whether the loose probe `_readObject` always tries first can find anything at all. The memo's lifetime IS the adapter object's, and `GitCommands.contextFor()` builds one adapter per `execute()` — so overlapping commands never share a view, and the memo is collectible as soon as the command returns. ANY write through the adapter drops it on both sides of the write (a reader can repopulate it while the write is still in flight). Never hang this memo off instance state, and never widen it across commands — that is the object/pack cache’s job (#2710, next bullet), and it is a DIFFERENT cache with its own invalidation precisely because it is allowed to outlive the command.
- **The object/pack cache lives on the `GitCommands` INSTANCE, not on the call** (#2710, `git-cache.ts`). isomorphic-git parks its parsed `.idx` files and read `.pack` buffers on the caller's `cache` object; SLICC passed none, so every command re-read the whole packfile (92 MB over the hostfs bridge on the slicc checkout), re-parsed all 30 indexes, and re-ran the deep SHA-1 payload check — 47 % of a warm `ls-files`'s CPU. `ctx.cache` is threaded into EVERY isomorphic-git call that accepts one; a new call site that forgets it silently pays the whole cost again. The two lifetimes are deliberately opposite: the #2709 read memo above is built per `execute()` and dies with the command (an adapter-level memo cannot see writes made straight to `ctx.fs`), while the object/pack cache is only worth having BECAUSE it outlives the command that filled it — which is why it carries its own invalidation instead of being thrown away. Four things keep a long-lived cache honest: the pack directory listing + `packed-refs` mtime are re-sampled before a command (but only for a repo the cache is already holding packs for, so #2713's "never touch `objects/pack`" property survives), `fetch`/`pull`/`clone` drop the repo's packs outright, at most `DEFAULT_MAX_RESIDENT_PACKS` pack BUFFERS stay in memory — the least recently used are unloaded while their parsed index (the expensive half) stays — and **every FAILED entry is evicted when the command settles**: isomorphic-git caches the in-flight promise, so one transient bridge `EIO` (#2720) would otherwise be memoized and every later command would await the same rejection with an unchanged pack listing to invalidate on.
- **The deep packfile SHA-1 is off by default** (#2710/#2735, `patches/isomorphic-git+1.42.2.patch`). Upstream hashes the whole pack payload before serving the first object, behind a flag it only sets AFTER the await — so every reader queued behind the pack read hashed it again (8-9 times for one 92 MB pack; the slower the transport, the more duplicates). The patch memoizes the verification as a promise on the cached pack and skips the payload hash when the cache carries `skipDeepPackVerification`; the O(1) trailer check always runs, which is already more than canonical git does on an object read. `$SLICC_GIT_VERIFY_PACKS=1` turns the deep check back on for a shell — and the memo records whether it INCLUDED the deep hash, so opting in mid-shell re-verifies instead of reusing the promise of the run that skipped it.
- **`--all` is ONE traversal, not one per branch** (#2712). `commands/log-walk.ts` seeds a committer-date priority queue with every `listBranches()` tip and yields commits newest-first from an async generator: each commit object is read exactly once, and because parents are expanded only after their commit has been yielded, a consumer that stops pulling never pays for the next generation. The `git.log({ ref: branch, depth: 50 })` loop it replaced also gave every branch its own isomorphic-git `cache`, so all 30 pack indexes were re-parsed once per branch; the walk now threads `ctx.cache` (#2710) through every read, so they are parsed once per SHELL — 157 s and 72,767 hostfs requests for `log --oneline --all -n 20` over 29 branches. Same-second timestamps tie-break by branch enumeration order then push order; ancestry needs no tie-break, because a parent is only queued once its child has been emitted.
- **Bound a history walk by what the caller asked for, never by a candidate window.** `--all -- <path>` filters the traversal AS IT RUNS and stops at `-n` matches or exhaustion. A fixed candidate cap silently loses matches: 500 commits on one busy branch would push another branch's matching tip out of the window with no diagnostic. Batching (`ALL_BRANCHES_PATHSPEC_BATCH`) is a filter-priming detail, not a bound.
- **Compare tree-entry oids, not whole trees.** "Did this commit touch `<path>`?" is `readTree` per path component in the commit and in its first parent, memoized per `(tree oid, pathspec)` across the walk. A directory's tree oid changes exactly when something below it changes, so a subtree pathspec needs no recursion. Pathspecs are exact-path-or-directory-prefix (`matchesPathspec` in `commands/revision.ts`), never globs.

## Speech

- Path: `packages/webapp/src/speech/`; entries `supplemental-commands/say-command.ts` and `hear-command.ts`. **Page realm only** (mic, AudioContext); kernel worker bridges via `hear-*` / `speak-*` / `synthesize-to-wav` panel-RPC. `say` plays on a TTY and writes 16-bit mono WAV to stdout when stdout is not a TTY or `-o -` is given (Kokoro-only; fail closed, never a zero-byte stream). just-bash never flags isatty on the command context, so `AlmostBashShellHeadless` registers `sayStdioPlugin` (`say-stdio-rewrite.ts`) which injects `-o -` when `say` is piped, redirected, or captured — TTY `say text` is unchanged. `hear -i -` and a non-TTY stdin (no `-i` / `-d`) read stdin once.
- Web Speech API (immediate) hot-swapped to on-device Whisper (`onnx-community/whisper-tiny`); Kokoro TTS (`Kokoro-82M-v1.0-ONNX`) chains off the whisper load. Kokoro selects on English + on-device readiness; Web Speech is fallback.
- Asset staging (`ensure-speech-assets.ts` via `kernel/speech-assets-bridge.ts`) is **single-flight**: the worker responder coalesces concurrent page requests (`hear --warmup`, `say --warmup`, the composer warmup) onto one run and fans progress/result out to every caller — never run two stagers over the same tree. `hf download` skips a present file only at the **listed byte length** (a torn write is re-fetched) and downloads over a pool bounded by file count and bytes in flight (`shell-reference.md`), and the ort install is gated on the required jsep + plain threaded builds only — optional `asyncify`/`jspi` variants missing must not trigger a `dist/` rewrite under a loading engine.

### Cancelling an abandoned browser command (issue #2417 follow-up)

`browser.withTab(targetId, fn, { signal })` makes a hold **abandonable**, so a `playwright-cli` command whose caller gave up (turn cancelled, `bash` `timeout`, `kill <pid>`) stops instead of running on. `playwright-command.ts` binds just-bash's `CommandContext.signal` into `PlaywrightHandlerCtx.onTab`, so every handler hold carries it without repeating it at ~60 call sites; `ctx.signal` is there for the steps a handler owns that the bridge cannot see. An aborted command exits **130** with the step it stopped at on stderr — never 0.

Primitives live in `cdp/command-abort.ts` — its own module because `har-recorder.ts` needs them and `browser-api.ts` imports the recorder, so keeping them in `browser-api.ts` would make the two circular. Cancellation is cooperative and lands at three kinds of boundary:

1. **Queued for the tab lock** — `acquireTabLock` rejects the queued caller at once. Its slot is chained to the predecessor (`prev.then(drop)`) rather than released early, or the next caller would drive the tab alongside the one still holding it.
2. **The attach handshake** — `attachLocalTarget` / `attachRemoteTarget` use raw `transport.send`, outside the handle's own boundary, so they gate explicitly and `attemptOnTab` re-checks before invoking the body. Without this an abort landing mid-attach still paid for `Target.attachToTarget` → `Page.enable` → viewport restore, each able to burn a transport timeout with the tab lock held.
3. **Inside the handle** — the signal is a private field on `TabHandle`, so `send()` checks before every session-scoped round trip (a multi-step operation stops at its next step), `navigate`'s `Page.loadEventFired` wait takes an `AbortWaiter` (`pending-request-table.ts`), and `waitForSelector`'s poll sleep rejects the moment it fires. One seam covers the whole page API, which is exactly what the session-explicit handle bought.

**A request already on the wire is not cancellable** — CDP has no cancel verb. The in-flight round trip still completes (or hits its own timeout) and may still have been applied to the page; what abort guarantees is that nothing after it starts and the tab's lock comes back as soon as it returns. `CommandAbortedError.step` says so; the `abandoned` stress scenario measures both halves.

`curlwright` is the other command on this path: `runPageFetch` takes the hold with the signal, and `runCurlwright` tests `ctx.signal` BEFORE `classifyFetchError` (whose `/aborted/i` branch would otherwise report a cancelled run as curl's exit 28, a timeout) and again before rendering, so no `-o` / `-D` file lands for a response whose caller has left. It exits 130 like `playwright-cli`, deliberately outside curl's vocabulary.

**Side effects that OUTLIVE the command need their own boundary.** `record` mints a recorder session on purpose so an LRU eviction cannot end a recording mid-flight, which puts the recorder's round trips outside the handle; it uses `throwIfCallerGaveUp` (`playwright/state.ts` — a plain `Error`, because `cdp/` is above the shell layer), passes the signal into `HarRecorder.startRecording`, and closes the tab it opened when it unwinds. `teleport` checks immediately before arming a watcher that polls on after the command returns.

### Follower prompt silence hint

A leader at tray protocol 10 or later acks each follower prompt with
`user_message_ack`, sent to the sending follower alone once it handed the
prompt to its kernel (`accepted`) or could not (`rejected`, with an `error`).
`accepted` does not mean the agent started: the handoff succeeds at once even
while the kernel is busy or starved. The leader
side is `deliverFollowerMessage` in `ui/wc/wc-tray.ts`, which resolves the
outcome off `workUnits.send()`, and `FollowerDispatch.ackUserMessage`
(`scoops/tray-leader/follower-dispatch.ts`), which sends it once it settles. A
prompt with no unit to deliver to is `rejected` at once with `scoopJid: ''`. A
biscotto's message is acked only after review approved it and it was delivered.

An older leader sends no ack. Its main thread still echoes the message at once,
but whether its agent ever picks it up only shows as later status frames and
agent events. `ui/wc/follower-prompt-watch.ts` arms on every accepted send
(`RemoteWorkUnitClient`'s `onSend`, which names the addressed unit) and disarms
on **any** reaction from the leader: an agent event, a biscotto review-state
frame, or a status frame. A dropped connection also disarms it. An `accepted`
ack does NOT disarm it; it counts like an echo. A `rejected` ack disarms it and
posts the leader's error as a
local note ("_The leader got that message but could not start it — …_") in the
addressed unit's thread. After 30 s of total silence it posts one local note to
the follower's thread, and the note depends on whether the leader echoed or
`accepted` the prompt:

- **No echo or ack**: the leader tab itself is not responding. It may still be
  starting, or be a background tab the OS has deprioritized.
- **Echo or `accepted`, no reaction**: the leader tab got the message, but its
  agent has not started on it. `FollowerSyncManager` still suppresses the duplicate bubble for
  its own echo, and reports the echo through `onOwnUserMessageEcho` instead.

In the extension side panel both variants point at **Bring leader to front**.
Both follower mounts wire the watch through the options bag (`onUserMessageAck`,
`onOwnUserMessageEcho`): the dedicated one (`wc-follower.ts`) and a
leader-capable float's tray role switch (`wc-tray.ts` `buildFollowerOptions`,
disposed with the role).

- A prompt queued behind a visibly running turn never trips it: that turn's
  events count as a reaction, and the queue already explains the wait.
- **Unit-scoped where the wire allows.** A status frame, echo or ack naming
  another unit does not disarm it or mark it received, and notes are posted
  only while the addressed unit is on screen (`addAssistantMessage` writes to
  the shown thread). Agent events carry no unit, so they disarm
  unconditionally. Every gap errs towards a missing note, never a misplaced
  one.
- It is separate from the channel-level stall (the leader stops answering
  pings), which disables the composer. This hint covers a live channel whose
  agent never reacts.

## Live model catalogue

pi-ai's catalogue is frozen at its release. `core/model-catalog.ts` layers pi's hosted catalogue over it, the same data `pi update --models` refreshes, so a model a provider launched after the pi-ai release shows up without an upgrade.

- **Read path.** `core/index.ts` re-exports `getModel` / `getModels` / `getProviders` from `core/model-catalog.ts`, not from pi-ai, and the external providers in `providers/` import them from there too. Every catalogue read sees one merged view: a remote model replaces a bundled one with the same id, and new ids are appended (pi's `mergeModels`).
- **Refresh path.** `ui/boot/setup-model-catalog.ts` is imported lazily after `registerProviders()` on the page and calls `core/model-catalog-refresh.ts` (kept out of the eager `core` chunk): it refreshes the catalogues behind the configured accounts (`getModelCatalogProviderIds`, which includes e.g. `amazon-bedrock` for `bedrock-camp`), then checks hourly. The network is touched only when a provider's stored copy is older than 4 h (pi's window). Requests go to the tray worker's `/api/models/providers/:id` relay, because pi.dev sends no CORS headers. The result is stored under `slicc_model_catalog` in `localStorage`, which `installPageStorageSync` mirrors into the kernel worker.
- **pi's freshness rule.** A stored catalogue whose `Last-Modified` is not newer than pi-ai's bundled generation time is ignored, so a pi-ai upgrade wins over an older overlay. The generation time is baked in at build time as `__PI_AI_MODELS_GENERATED_AT__` (`vite-plugins/pi-ai-model-data.ts`); importing pi-ai's `getBuiltinModelDataGeneratedAt()` would bundle its whole data manifest into the boot graph.
- **SLICC's guards.** A remote model is dropped unless its `api` **and** `baseUrl` already appear among that provider's bundled models. This stops remote data from redirecting where an API key is sent, and it keeps an API route SLICC's pinned pi-ai cannot stream from reaching the picker. For example, pi.dev serves some OpenRouter Claude models over `anthropic-messages` at `https://openrouter.ai/api`, which pi-ai 0.84.4's OpenRouter catalogue never uses, so those entries keep their bundled definition. Only the `Model` fields SLICC relies on are copied (never `headers`), and malformed entries are dropped one by one.
- **Kill switch.** The `live-model-catalog` flag (worker `FEATURE_FLAGS`) turns the overlay off in both realms. The stored data is ignored, not deleted.

## Budget-mode cost surfaces

A provider that bills against a **rolling allowance** rather than per token makes session
dollars the wrong headline: a family-priced model can bill $0.00 while the shared window burns
down. Three providers report one:

- **Adobe** — one 7-day window over `GET /v1/usage` on the LLM proxy (OpenCode Go's public
  shape, same IMS token as `/v1/messages`).
- **xAI Grok** — the rolling SuperGrok allowance behind the grok.com Settings > Usage tab, over
  `GET https://cli-chat-proxy.grok.com/v1/billing?format=credits` with the OAuth access token.
  The route is **unofficial and undocumented** (it is the JSON transcoding of the gRPC-web
  `GetGrokCreditsConfig` the web app calls, and `api.x.ai` has no usage route at all), so
  `providers/xai-grok-usage.ts` caps the body before parsing, clamps the percent, and degrades
  to "no window" on any shape it does not recognise. Dropping `?format=credits` silently returns
  the monthly RPC's shape instead.
- **GitHub Copilot** — the account's rolling monthly premium-interaction allowance (AI
  Credits), over `GET https://api.github.com/copilot_internal/user` — the same bootstrap call
  the official `copilot` CLI makes at session start — authenticated with the raw GitHub OAuth
  access token (`PersistedCopilot.githubAccessToken`, stored as `account.refreshToken`), not the
  short-lived Copilot completion token. Only `quota_snapshots.premium_interactions` is metered;
  `chat`/`completions` report `unlimited: true` on every plan seen so far, so an unlimited
  premium window also degrades to "no window" rather than a 0%-used reading.

- **Provider hook** — `ProviderConfig.getBudgetUsage?()` (`providers/types.ts`). Its contract is
  a three-way answer, and the distinction is load-bearing for the cache: `null` = "this provider
  has no budget concept / the proxy lacks the endpoint" (re-probed in 30 min), **throw** = "the
  call failed" (retried in 5 min, previous reading stays on screen), a window = a reading.
  All three implementations are pure modules with an injectable `fetch`, so they are testable
  without network (`providers/adobe.ts` itself cannot be imported under vitest):
  `providers/adobe-usage.ts`, `providers/xai-grok-usage.ts`, and
  `providers/github-copilot-usage.ts`. A 404/501 is an answer — and the likeliest way an
  undocumented route retires — while every other non-OK status is a failure; Grok's 401/403
  throws a "re-login required" message rather than reaching a render path.
- **OAuth token masking (`oauthTokenDomains`)** — a budget endpoint on a host the provider does
  not declare in `oauthTokenDomains` has its token **masked**, and the fetch proxy then drops
  the request CLIENT-SIDE: no HTTP status, no body, which reads like a network outage rather
  than an auth problem. `cli-chat-proxy.grok.com` is in xai-grok's list for exactly this reason.
  At runtime the same fix is `oauth-domain add <provider> <host>` then `oauth-token --renew`.
- **Cache** — `providers/budget-window-cache.ts`: success 60 s, failure 5 min, unsupported
  30 min, one shared in-flight probe, keyed by provider id so a switched account never inherits
  the previous one's allowance. `providers/budget-usage-source.ts` is the singleton over it.
- **Wire** — `SessionStatsMsg.budget` (`kernel/messages.ts`), attached by `facade.ts` from the
  SYNCHRONOUS snapshot; the refresh is fired and forgotten because the handler sits on the
  request loop. The one exception is a session's FIRST pull, which waits up to
  `FIRST_BUDGET_PROBE_MS` (2.5 s, under the panel's 5 s stats timeout) so a budget provider's
  pill leads with its window instead of showing `$/h` and then flipping.
- **Surfaces** — `ui/wc/wc-monitor.ts` (budget hero, demoted burn tile, Cost group named by the
  window, warn/refusal alerts), `ui/wc/wc-live.ts` (floatbar `budget` property), and the `cost`
  command via `registerSessionBudgetProvider` (registered beside the costs provider in
  `orchestrator.ts` and `kernel/host.ts`).
- **Conventions** (shared with `@slicc/webcomponents` — see `docs/webcomponents-details.md`):
  percent **USED**, never remaining; the bar clamps at 100% where the figure does not;
  `rate-limited` is critical whatever the percent says; reset copy is relative and locale-free
  (`resets in 18h`), formatted at the reading edge from the ISO `resetsAt` on the wire.
  `providers/provider-budget.ts` holds the parser, the thresholds and the copy — deliberately
  duplicating the webcomponents formatter so the shell keeps a DOM-free copy, with
  `tests/providers/provider-budget.test.ts` pinning the two together.
- **`cost --json` is an envelope**: `{ "budget": <window|null>, "scoops": [ … ] }`, and it is now
  parseable in the no-data case too (it used to answer with prose).

### Exhausted provider budgets

An exhausted allowance is a user-remediable state, not a transient transport failure.
`core/error-families.ts` owns the provider-neutral classification and detail shape used by the
retry loop, chat card, read-only transcript, and telemetry filter:

- Adobe's structured `429` is exhausted only when its envelope contains
  `error.type: "quota_exceeded"`; its message and optional `resets_at` are preserved.
- Grok's `403` is exhausted only when the body contains both the out-of-resources/credits phrase
  and the active-subscription phrase. A generic 403 is still an authorization failure.
- A plain `429 Too Many Requests` or ordinary rate-limit message is transient and keeps the
  bounded retry policy.

`scoops/scoop-context/error-classification.ts` consults this family before status-based retry
rules. `ui/wc/wc-message-view.ts` renders **Out of AI budget** with switch/add-provider actions,
never plain Retry; read-only transcripts keep the readable body and omit actions. The same family
is intentionally dropped from RUM because it already has dedicated remediation. The iOS follower
mirrors the response cases and copy in `Models/ErrorFamilies.swift`, while remaining actionless
because provider changes are leader-side state.

Both summarized and naive-fallback threshold compactions are adopted into pi's active-loop snapshot and `Agent.state.messages`, then persisted immediately; returning a transformed request without that adoption makes every tool continuation compact the same oversized prefix again. A threshold/overflow fallback is therefore durable rather than retried on every continuation, while the full pre-compaction transcript remains recoverable from the Markdown archive. `CompactionOptions.trigger` (`threshold` / `overflow` / `idle`) rides the `compaction-state` envelope; `offscreen-client.ts` maps phase → marker state and emits ONE `compaction_notice` per round (never a fake assistant turn — that stranded `#processing`), which `wc-chat-controller.ts` renders as `<slicc-compaction-marker>` and removes again on `discarded`. Compact on idle (graduated; `compact-on-idle` survives as the central kill switch `idleCompactionEnabled` reads, and the gelatiere ignores both it and the roots-only rule): `scoop-context/idle-compaction.ts` arms on `ready` (roots only), gates on `core/idle-compaction-settings.ts` (defaults overridable live via clamped `slicc_idle_compaction_minutes` / `slicc_idle_compaction_min_tokens`, which is how the e2e drives a sub-minute window), aborts on prompt/stop/clear/dispose, sets `allowNaiveDrop: false`, defers memory extraction until the result is adopted, adopts only a successful non-empty summary when the thread did not move, and fires `onDiscarded(roundId)` for every non-adopted started round so the row is retracted. Any idle summary failure (rate limit, quota/auth/provider error, empty/malformed response) returns the exact input array, skips canonical persistence, keeps the transcript snapshot, re-arms the idle window for a later retry without waiting for another `ready` transition, and carries only a non-sensitive `failure` class through the terminal state for diagnostics; active threshold/overflow recovery retains the emergency naive-drop policy. The round id is what makes a LATE retraction safe: the compactor emits its terminal state (and the panel settles the row) before adoption is known, so `offscreen-client.ts` keeps the settled row in `compactionSettledRows` and lets a `cancelled` naming that same round take it back — while a discarded round that never opened a row (nothing to summarize) leaves an earlier round's row alone. An aborted or failed idle round returns its input history untouched and emits `cancelled` instead of `fallback`. Index writes from both realms share the `slicc:sessions-index` Web Lock; "Erase" deletes the snapshot in the kernel via `clear-chat { discardLiveSnapshot }`. Details: `docs/tools-reference.md` § Context Compaction. Behind `memory-v2`, a scoop compaction uses the same snapshot writer under `/scoops/<folder>/sessions/<jid>/` (sandbox-writable; `/sessions` stays cone-only; JID isolates drop-then-recreate lifetimes). Scoop archives are never enrichment-renamed — the live path is the permanent pointer for that registration; a pointer into a deleted scoop is acceptable only after `drop_scoop`. With `memory-v2` and `agentic-memory` both on, each cone round schedules a curator slice of the live archive (`curatedThrough`, parallel to `liveThrough`) after the snapshot is durable — compaction itself still builds no memory (#2003) — and `memory dream` runs the same slice before the dreamer. Receipts are keyed per delta, so "New chat" mines only what that cursor has not covered.

## Memory files and `memory_write`

Durable memory (`/workspace/CLAUDE.md`, `/cones/<f>/CLAUDE.md`, `/scoops/<f>/CLAUDE.md`,
`/shared/CLAUDE.md`) and a curation pass's staged draft (`/sessions/.curation/<key>/draft.md`) are
**budget-governed**: `base/memory-budget.ts` owns the budget formula (`computeBudget`) and the
path predicate (`isMemoryFilePath` — deliberately not "any `CLAUDE.md`": a repository's developer
docs under the workspace are not memory).

- **One write path.** `fs/memory-guard-fs.ts` wraps the sudo-gated handle the file tools and the
  shell share, so `write_file`, `edit`, `cp`, `cat >` and `node -e` all get
  `EACCES … use the memory_write tool` on a memory file. `tools/memory-write-tool.ts` is handed the
  pre-guard handle (`ShellAndSkills.memoryFs`) and is the only writer.
- **The rule.** Under budget any write lands; over budget a write lands only if it **shrinks** the
  file; a file never crosses the budget upward. Whole-file `content` or exact `edits` — both compute
  the result first and gate it the same way, so a cone recording one fact does not re-emit 80 KB.
- **The report.** Every success returns the size that landed and the remaining room or overage
  (`Wrote …: 9323 chars, 1596 under the 10919-char budget.`), so a curator never spends a turn on
  `wc -c` (#3157: the dreamers that tripped their wall clock spent it re-emitting whole files and
  re-measuring). The budget is read per call from `/sessions/index.json` via the ungated handle.
- The runtime's own writers (the freezer's legacy append, the bridge's staged-draft merge, the
  `update_global_memory` callback) use the shared VFS directly and are not guarded.
- **Trip promotion.** Because the staged draft can only change through `memory_write`, a pass cut
  off at its wall-clock or turn bound (`isRunBoundTrip` in `agent-bridge.ts`) has its diverged
  draft folded in as a truncated success: exit 0, `merge.promotedOnTrip: true`, and the bound
  note kept under `reason` in `status.json`. A draft that never diverged, or any other failure
  (provider error, abort), keeps the staging pair for a post-mortem and the live file untouched.
  The cone's `scoop-notify` for these passes is deferred until that receipt is written (#3460): a
  non-zero exit headlines as `[@… failed]` with `status` / `exitCode` / `reason` and a
  `status.json:` path; a truncated success still headlines as `completed` (with the bound note).

Modal because the composer owns focus almost always: an unmodified letter would fight typing, and every modifier chord collides with the browser (⌘+digit, and Ctrl+digit off macOS, are its tab switcher). **The mode is the RESTING state under the default `trigger: "auto"`**: `settle()` (deferred, coalesced) asks `deepActiveElement()` whether anything typable — or any composer chrome (`isWithinElement(composerBand, …)` or a pointer currently down on the band, so send / `+` / the model pill cannot flip the mode on mid-click even when they drop focus) — holds the focus and turns the mode on when nothing does — at boot, after any blur, after a command hands focus to a panel — so the answer to "will this letter type or command?" is always visible (caret in the composer, or badge up). `/etc/slicc/keys.json` `"trigger"` may also be `"esc"` (only Escape enters) or `null` (disabled); Theme settings switches it live via `setTrigger` + `writeShortcutTrigger`. Escape is therefore not a toggle: the **first press `preventDefault()`s and leaves the field**, and a press made INSIDE the mode has nothing left to leave, so it is spent on fullscreen and calls `exitFullscreen()` explicitly, because this module requests Keyboard Lock (`navigator.keyboard.lock(['Escape'])`) while the document is fullscreen and the browser then never acts on Escape itself. Two consequences of an always-on mode, both load-bearing: a focused BUTTON keeps its own Enter/Space (`isActivationTarget()`, or a tabbed-to control could never be pressed), and `settle()` skips a document that is not focused (`doc.hasFocus()`) so an unfocused Cherry iframe does not wear a badge for a keyboard it does not have — a window `focus` listener re-settles it. The mirror of that rule points INWARD: a frame element holding the focus (`isFrameTarget()` — a sprinkle panel, a dip's approval card, a Cherry mount, anything a rail hosts in an iframe) is where this document's focus stops, so every keystroke is delivered to the frame's own document and never reaches the listener. The mode is dropped there too — inline on `focusin` as well as in `settle`, so the badge does not outlive the focus by a macrotask — and, like a window blur, it is a SUSPENSION (`settler.suspend()`): the `ModeIntent` is untouched and the mode returns with the focus. A suspension has to be REMEMBERED rather than recomputed, because `esc` never auto-enters: under it, a mode the user pressed Escape for and a frame (or another window, the same defect) took away would otherwise be lost for good, so `settle` puts a suspended mode back explicitly — while a live `setTrigger` drops the record (`dropSuspension()`), because a switch DECIDES the mode and must not be undone by one. Removing the focused frame needs its own watch: `activeElement` resets to the body with no `focusout` at all, so a reloaded or closed sprinkle (`SprinkleRenderer.dispose()` removes the iframe) would leave the mode suspended for a frame that no longer exists — a `MutationObserver` living only while a frame holds the focus, whose callback is one `isConnected` test, schedules the settle instead. `settle()` runs on a TIMER rather than inline because a tab click blurs the composer BEFORE it moves the selection: inline, that gap would read as "the user left the composer" and cost them the caret they were about to get back. It is also scheduled AFTER a `holdsMode: false` command, because that flag is a prediction that the surface will take the focus and not a fact — `dock.selectItem()` only emits a selection, and the files and memory panels focus nothing, which would otherwise strand the mode off with nothing focused (badge gone, letters dead). Window `blur` clears the mode outright: with the focus already on nothing there is no `focusout` to notice the window leaving, so the badge would keep claiming keystrokes now going to the host page or another app; the intent is left alone and the `focus` listener settles it back. **Switching units carries the mode across** — a `ModeIntent` (`'composer' | 'keyboard'`), restored by a `MutationObserver` on the strip's `active` attribute, which is what every float already writes on a selection (`applyThreadContext`, the follower's select handler, and therefore the freezer rail and the cone actions too — no float has to remember to call anything). The intent is written only while `composerAvailable()` says a composer exists, which is the whole subtlety of the cone → scoop → cone detour: a scoop is read-only and its composer band is `hidden` (#2312), so the keyboard mode it forces is not a choice and must not overwrite the caret the cone left behind. A switch the user did not make (a sprinkle's `slicc.selectScoop`, a follower re-pointed off a unit that left the roster, the first cone at boot) must not take the keyboard from someone typing: a user's own switch never finds a text field focused, so `restore()` that finds one leaves the caret and the mode alone; the sprinkle bridge refuses a switch outright while the focused composer holds a draft (`composerHoldsDraft`, `wc-unit-context.ts`), because the draft is not per unit and would be readdressed; and `<slicc-input-card>` gives back a caret its `disabled` took (follower connection loss, a thawed archive) when the focus is still on nothing at re-enable. The other half of an always-on mode is a component's own keyboard shadowing it: `<slicc-agent-tabs>` claims ←/→ for its roving tablist walk and `preventDefault()`s them, and the mode stands down for a key something closer already claimed — so with the focus resting on a tab segment (where a click leaves it) the strip shuffled its focus ring while `nextAgent`/`prevAgent` never ran. The mode therefore sets the strip's `arrow-keys` to `off` for as long as it is up (`ShortcutSwitcher.arrowKeys`), yielding those two keys and leaving Home/End and Enter/Space activation where they were. An Escape belonging to an open overlay is never taken: `<slicc-dialog>`/`<slicc-tab-overlay>` stop propagation in capture, `<slicc-permissions>` marks it handled, and `<slicc-quick-look>` does neither — which is the entire reason `hasOpenOverlay()` exists. The mode indicator IS the key HUD, and it is a component: `<slicc-key-hud>` (`@slicc/webcomponents`), mounted by `createHud()` on the CHAT COLUMN — `refs.chatPane`, not the composer band, because a read-only scoop hides its band entirely (#2312) and a mode indicator that vanishes exactly where the keyboard is the only way to drive is worse than none. It pins itself to the column's bottom edge, which with a visible composer is the band's, over the meta row. The shell owns only what it knows: where it mounts, `linger` (written from `HUD_LINGER_MS` so it cannot drift from `CHORD_WINDOW_MS`, which is the same number by design), and the `hint`, built by `hudHint()` from the keymap in force — the help key and every key bound to `composer`, in the element's `[x]` cap notation, so a rebind can never leave it naming a dead key and both ways back to typing are stated (`i` and Enter; Escape is not one, it ENTERS the mode). Presses are forwarded press-by-press with a `bound` flag; the drawing rules (stale dimming, depth, the linger clearing back to the hint, a press that ran nothing shown dimmed rather than dropped) are the component's own contract. While the mode is up the band carries `keys` and everything in it recedes to 55% except the HUD, so the one thing at full contrast is the one thing the keyboard is talking to. `describeKey()` returns an ARRAY of caps (modifiers then key) so a future multi-key chord is the same shape with parts from more than one event; the strip is `aria-hidden` so the badge's live region announces the mode, not every keystroke. While ANY modal is open every command is suspended except closing our own help overlay, so a shortcut can never act behind a dialog (focusing the composer under it, switching the agent it belongs to); Escape is handled before that gate, so a modal is always dismissable. The listeners live on the DOCUMENT while `mountWcShell` is idempotent, so `wireKeyboardShortcuts` keeps ONE installation per document (`INSTALLED` WeakMap) and a remount disposes the previous wiring — otherwise the first one keeps running, first, against the detached shell. Keys map onto stable `CommandId`s, not onto internals, which is what makes `/etc/slicc/keys.json` (`ui/wc/wc-shortcut-config.ts`) possible: `DEFAULT_KEYMAP` ships in code, the file overrides it, and `shortcutRows()` DERIVES the help sheet from whatever is live so a printed list can never disagree with the keyboard. Seeded once from `packages/vfs-root/etc/slicc/keys.json`, which now ships with `"trigger": "auto"` and NO bindings — v1 wrote its sixteen out explicitly and, since the file is applied over the defaults, thereby pinned every install to the v1 keyboard forever, so a file still holding it exactly (`isUntouchedV1Document`) is replaced once and anything edited is left alone. Loaded lazily off the boot critical path (a VFS read from boot starves the terminal's lazy mount) and applied over the defaults the shell already wired. **Chords** extend the digits onto any surface that owns an ordered list (`Command.list` → `ShortcutList` in `ui/wc/wc-shortcut-surfaces.ts`): the prefix runs EAGERLY and arms one key of lookahead for `CHORD_WINDOW_MS`, so `f 3` opens the files panel and then its third row while a lone digit still addresses the tab strip, `indexForDigit` gives every list the strip's own "9 is the last one" rule, and a list command therefore HOLDS the mode — dropping it would mean the completing key arrived with the keyboard off, one macrotask before `settle` turned it back on. The armed chord carries the INDEX it is standing on (`ArmedChord`), which is what makes the step keys (`j`/`k` → `stepList`) page a list with looping and re-arm it, so `f j j j` keeps walking; `Command.run` may RETURN the index it activated to seed that (`sprinkles` opens the first and returns `0`, so `e j` is the second — which is why there is no dedicated cycle key). With nothing armed the step keys walk the transcript instead (`scrollMessage`, position-based off the thread's own box). `CHORD_WINDOW_MS` is deliberately `HUD_LINGER_MS`: a chord is live exactly while its caps are on the pill, and both are refreshed by the same presses. `wc-shortcut-surfaces.ts` is the shell half: the commands that reach their surface through the DOM rather than a component method (the send button's `stop`, the copy row's press gestures, the add menu's `open()`, an approval card's button, `requestFullscreen` on the open panel — synchronous inside the keydown, because that is the only place the keystroke still counts as transient activation), each a silent no-op on a float that lacks the surface. ## File mentions + preview

Clicking a file name the agent wrote in chat. Five modules, deliberately split so the guessing and the verifying stay separate:

- `core/file-mentions.ts` — the heuristic. Pure; finds CANDIDATES in prose and knows nothing about the VFS.
- `core/tool-call-paths.ts` — harvests the paths a tool call's parameters named (bash redirects, `path`-ish fields), so prose can be read against what the agent already did.
- `core/file-mention-resolver.ts` — checks candidates against the VFS via a lazily built, bounded basename index, with those paths as hints.
- `ui/file-mention-linker.ts` — walks a rendered message and links only what resolved.
- `ui/wc/wire-file-mentions.ts` — lifecycle: observes the thread, waits for streaming to finish, opens the preview.

Plus `core/file-type.ts` (content sniffing) and `ui/git-preview-source.ts` (the HEAD blob for diff mode). `ui/wc/file-actions.ts` owns `openFilePreview`, the single entry point both the file tree and a clicked mention go through.

Non-obvious rules:

- **Confirm, then linkify.** Nothing is decorated optimistically — the heuristic is permissive precisely BECAUSE verification gates it. A candidate that does not resolve stays plain text.
- **Never linkify a streaming bubble.** A half-arrived path resolves to nothing; bubbles are processed only once `streaming` clears.
- **`getMimeType()` (`core/mime-types.ts`) is for SERVING, `sniffFileType()` (`core/file-type.ts`) is for READING.** Never swap them: sniffing a type you then put in a `Content-Type` header is how MIME-confusion bugs happen, and serving's conservative `application/octet-stream` fallback is exactly what made `.jsh` unpreviewable. Precedence is magic bytes → extension → UTF-8 decodability.
- **`isomorphic-git` is imported lazily** in `git-preview-source.ts`; the UI layer must not pull the `src/git/` stack for a preview. Its fs shim is read-only ON PURPOSE — a preview surface must never be able to write to a repo.
- **Hints come from the typed `ToolCall`, not from parsed markup.** `wc-message-view.ts` stamps each rendered tool row with `data-file-paths` (JSON) at render time; `wire-file-mentions.ts` reads the rows that PRECEDE a bubble in document order — chronological in a transcript — capped at the most recent 40. A hint is believed only after `stat()` confirms it, which is what lets it resolve a file outside the indexed roots (`/home/lars/foo.md`) without ever inventing a link.
- **A hint without a directory is dropped.** The whole value of a hint is the path segment prose does not carry; a bare basename tells the resolver nothing the index did not already know, and would only cost a `stat()`.
- **Markdown is detected by EXTENSION, on purpose** (`richPreviewKind` in `core/file-type.ts`). It has no magic bytes and is byte-identical to plain text — the name is the only declaration there is, and being wrong changes only which view opens first. Markdown is converted by `ui/message-renderer.ts` (DOMPurify-sanitized) and mounted inline; **raw HTML is never sanitized and never mounted inline** — it goes to Quick Look's sandboxed iframe. Documents over 512 KB get no rendered view (synchronous conversion would freeze the overlay).
- **The mention resolver's index is bounded** (`maxEntries`, `maxDepth`, skipped `node_modules`-class directories). A mention that would only resolve past the ceiling stays plain text; stalling the transcript to prove otherwise is worse.

## Base64 payload previews

A payload PASTED into chat — a `data:` URL, the output of `base64 < key.pem` — collapses to a `<slicc-blob-chip>` that opens it in Quick Look. Same four roles as file mentions (`packages/webapp/CLAUDE.md`), and reusing the same machinery rather than growing a second copy of it.

- Path: `core/base64-mentions.ts` (heuristic, pure) → `core/base64-payload.ts` (decode + identify) → `ui/base64-preview-linker.ts` (DOM swap) → `ui/wc/wire-base64-previews.ts` (lifecycle + Quick Look, wired from `mountWcShell`). Chip: `<slicc-blob-chip>` in `@slicc/webcomponents`.
- **Consolidated, not duplicated.** The base64 grammar is `normalizeBase64` in `@slicc/shared-ts` (shared with `base/image-markers.ts`); decoding is `base64ToUint8`; identification composes `sniffMagicBytes` / `looksLikeText` / `isTextMimeType` from `core/file-type.ts`; the synthetic filename comes from `extensionForMimeType` in `base/mime-types.ts` (reverse index of the SAME table `getMimeType` reads); the rendered view is `file-actions.ts`'s `buildRenderedView`, so the 512 KB cap and the inline-vs-sandbox rule have one home; the chip's short type label is `@slicc/webcomponents/quick-look/mime-label`, shared with Quick Look's header chip.
- **Three shapes, not one.** A `data:` URL, a bare single-line run, and the COLUMN-WRAPPED block `base64`(1) emits by default (76 columns; PEM uses 64). The wrapped shape is the advertised `base64 < report.pdf` scenario and its individual lines are each far below the length bar, so it needs its own pass — believed only when it has the exact shape an encoder produces: two or more whole lines, every one but the last the same width and a whole number of quanta, only the last carrying padding, and no more of the block after that last line (without which a ragged 76-then-72 pair of PROSE lines reads as a complete block). A first line that carries the user's own words in front of the paste (`here it is: <76 chars>`) is glued back on when its trailing run is exactly one wrap column wide — otherwise the block would be claimed from its second line, stranding the first 76 characters as text beside the chip.
- **The DOM half has to match.** `marked` runs with `breaks: true`, so a wrapped paste arrives as `text <br> text <br> text` — one node per line. `ui/base64-preview-linker.ts` therefore walks SEGMENTS (maximal runs of adjacent `Text`/`<br>` siblings, joined with `\n` per `<br>`), not individual text nodes; any other element ends the run, because across a `<strong>` the text was never contiguous. `<br>`s that fall inside an elided span are removed with it, or a collapsed block leaves a stack of blank lines where its wrapping used to be.
- **Eliding is destructive in a way linking is not.** A wrong file mention is a dead link; a wrong base64 match HIDES text the user typed. So the heuristic is the conservative twin of `file-mentions.ts`: ≥128 alphabet characters (`MIN_PAYLOAD_CHARS`), a whole number of quanta, and an explicit small delimiter set — a leading `.` opens nothing, so a JWT's middle segment is never clipped out from between its neighbours, while a trailing `.` closes a run so a payload can end a sentence. Then the bytes still have to decode to something recognizable: `identifyBase64` returns `null` (magic → declared → UTF-8 decodability, all misses) for a hash or an opaque id, and the run stays exactly as typed.
- **A `data:` URL's declared type is evidence, not proof.** Magic bytes outrank it, and `application/octet-stream` is not a claim at all — the bytes get the last word.
- **It covers USER messages, which file mentions do not**, because a pasted blob is overwhelmingly something the user pasted. A user bubble renders into a SHADOW root, which the thread's `MutationObserver` cannot see into: the host is processed on add / attribute change and `shadowRoot .b` is queried directly. That works because a user bubble only re-renders from an attribute change — its content is set before it is connected.
- **No VFS, ever — which is why it wires at the FRAME.** Verification is a synchronous decode, so `wireBase64Previews` is called from `buildWcShellFrame` (`ui/wc/wc-shell.ts`), not from the workbench phase (`attachWcWorkbench`). That matters for reach, not just boot cost: a follower — Cherry, the tray follower, the extension side panel — mounts the same frame and the same chat surface but no workbench (#2382 D2b), so anything wired in the workbench phase never runs there. `buildWcShellFrame` is the one seam every transcript-rendering surface passes through, the design-time fixture included. File mentions genuinely belong in the workbench phase — they need a VFS reader a follower has no worker for — but a decode needs nothing.
- **`pre` is skipped, inline `code` is not.** A code block already scrolls inside itself and is the one place someone is asking to see the literal characters.
- **The elision is presentation only.** The persisted `ChatMessage.content` is untouched, so clipboard copy (`ui/chat-clipboard.ts`), transcript export and agent replay all still carry the full payload.
- **Long strings that are NOT payloads still have to wrap.** Both chat prose surfaces carry `overflow-wrap: anywhere` (`slicc-user-message`'s `.b`, `slicc-agent-message`'s `.body`); fenced code opts back out. A `max-width` cap does not contain an unbroken run — the box stays capped and the text spills out of it. Test it with `scrollWidth` vs `clientWidth`; a box-width assertion passes either way.

## Mention previews (links, GitHub refs, times, questions)

Hover cards for four more things an agent writes in prose. Same shape as file mentions: a cheap pure heuristic in `core/`, a DOM decorator in `ui/mention-previews.ts`, and lifecycle in `ui/wc/wire-mention-previews.ts`. One shared `<slicc-hover-card>` (`@slicc/webcomponents`) serves the whole thread; content is `<slicc-link-preview>`, `<slicc-time-preview>` or `<slicc-question-prompt>`.

- Links: `core/og-meta.ts` (parses `og:*` / `twitter:*` / `<title>`) + `ui/link-preview-fetcher.ts` (proxied fetch, bounded cache, timeout). GitHub refs: `core/github-mentions.ts` finds `#123`, `owner/repo#123` and GitHub URLs; the card image is `opengraph.githubassets.com`, so it needs no API token.
- Times: `core/time-mentions.ts` over `gpu-time` (pinned exact; CPU backend, lazy-imported on the first message that `mayContainTime`). Questions: `core/agent-questions.ts` classifies a sentence as yes/no, number, date, date-time, email or free text.
- **Fetch on hover, never on render.** Rendering a link costs nothing; the first hover fetches once and the result is cached (failures too), so a transcript full of links does not fan out requests. The proxied fetch is built with `maxResponseBytes` (2 MiB) and the request is aborted on timeout: `SecureFetch` buffers a whole body, so slicing afterwards would not bound the download.
- **Relative times resolve against the message, not now.** `wc-message-view.ts` stamps `data-msg-time` (epoch ms) on each agent bubble; "tomorrow" in last month's message is parsed from that instant. The card's relative label and today marker still use the real now.
- **The repo for a bare `#123` is inferred, like a file mention's directory.** Hints come from the preceding tool rows and messages (GitHub URLs, `-R`/`--repo`, `gh repo clone|view|fork`, qualified refs), most recent wins, capped at the last 40. When prose gives none, `core/git-remote-repo.ts` reads `.git/config` (origin → upstream → any GitHub remote) walking up from the tool rows' path hints. No repo, no link: a `#3` in a numbered list stays plain text.
- **gpu-time needs help with prose.** It merges clauses ("tomorrow at 9am and check back in 20 minutes") and matches filler ("Now,"), so `findTimeMentions` splits clauses, re-parses around conjunctions, drops filler spans and keeps confidence ≥ 0.8.
- **Only the latest agent message is answerable.** A question is inert (card shown, controls disabled) when it is in an older message, the user already replied after it, the message is still streaming, or the unit is read-only (composer hidden). Answering sends a `question` sprinkle lick `{ action: 'answer', data: { question, kind, answer, timeZone? } }` (a date-time answer carries the answerer's UTC offset, and date / date-time answers add the IANA `timeZone`) to the unit whose transcript asked (`ui/wc/question-answer-lick.ts`, wired in `wc-live-controller.ts`), exactly like an inline dip's lick.
- **Wired at the frame, VFS attached later.** `wireMentionPreviews` runs from `buildWcShellFrame` (links, times and questions need no VFS); `attachMentionPreviewFs` adds the git-remote fallback once the workbench has a VFS. `pre` is skipped, idempotency is a content fingerprint, and the persisted message content is untouched.

## Sprinkles & Dips

- Attention-mode sprinkles are parked until selected. `SprinkleManager.activate()` must both promote them to user-opened and re-place the existing container; updating persistence alone leaves the first rail click with a selected icon and hidden content.
- Renderer-changing operations are serialized per sprinkle. A VFS write schedules an automatic reload, so it can overlap an explicit `sprinkle open` / `sprinkle reload`; concurrent renders append sibling iframes into one panel and leave all but the last untracked. Different sprinkle names keep independent queues.
- Sprinkles: `ui/sprinkle-renderer.ts`, `sprinkle-manager.ts`, `sprinkle-discovery.ts`. `.shtml` panels discovered from VFS. **Discovery is bounded** (issue #2717): `/shared/sprinkles` first, then the `SPRINKLE_ROOTS` in `base/sprinkle-roots.ts` (`/workspace`, `/shared`, `/scoops`, `/home`) — six levels deep, skipping `node_modules`/`dist`/`build`/`coverage` and dot-directories, via `fs/bounded-walk.ts`. It used to walk `/`, which on the page side is one worker RPC per directory and, under a `--mount`, one `/api/hostfs/list` each; a mounted checkout put the boot crawl inside `node_modules/…/.build/…` at depth 11, competing with the cone's own commands for the browser's 6-connection pool. The same constant drives the `.shtml` watchers in `kernel-worker.ts` and `SprinkleManager.setupWatcher`, so what is watched and what is discovered can't drift. Never point `walk` at `/` from the page side. CLI: fragments/full docs in `srcdoc` iframes. Extension renders in the hosted `?cherry=1` follower — no extension sandbox.
- Sprinkle delivery + routing (issue #2166): one store, many documents. `SprinkleManager.sendToSprinkle` returns a `SprinkleSendReport` (`shell/sprinkle-manager-handle.ts`) instead of void, and its broadcast hook fires even when the sprinkle is CLOSED on the leader — a follower can still be rendering it. Targeted delivery goes `sprinkle send --runtime` → hook → `tray-leader/broadcast.ts#broadcastSprinkleUpdate` → `resolveFollowerByRuntimeId`; an unresolvable runtime comes back as `unknownRuntime`, never as a silent broadcast. Followers report rendered documents with `sprinkle.instances`; the leader keeps them per-follower in `FollowerRegistry` and `wc-tray.ts` mirrors them into `slicc.leaderSprinkleInstances` so the worker-side `sprinkle list` can read them (same shim pattern as `host`). **Route resolution belongs to the leader**: `KernelFacade.routeSprinkleLick` falls back to `getSprinkleRoute(name)` when the caller stamped no `targetScoop`, which is the only thing that applies a route to follower-forwarded licks.
- Sprinkle element bundles (`<slicc-diff>` / `<slicc-editor>`) ride the app's chunk graph: they are Rollup entries (`build.rollupOptions.input`) whose stable-name loader shims (`dist/ui/slicc-diff.js` / `slicc-editor.js`) dynamic-import the hashed entry, so Shiki / `@pierre/diffs` / CM6 stay the SAME chunks the app ships, not a second eager copy (`slicc-diff.js` alone was 5.8 MB as an esbuild IIFE, because esbuild inlines dynamic imports). **Loading is async, so two invariants hold:** the elements must adopt pre-upgrade properties (`ui/upgrade-own-properties.ts`) — a sprinkle that assigns `.patch` / `.value` on an element BEFORE its definition finishes loading installs an OWN data property that shadows the upgraded accessor forever, so the setter never runs and the diff/editor renders blank; and a sprinkle awaiting a method API must wait on `window.__SLICC_SPRINKLE_ASSETS__['slicc-diff.js']` rather than assume the element is already upgraded.
- Sprinkle disclosures: `<details>` keeps native mouse and keyboard behavior in both inline fragments and full-document iframes. Only the trigger belongs in `<summary>`; put text that should collapse in a sibling after it. A source with an explanation but no detail rows otherwise looks stuck even though `open` toggles correctly. Custom chevrons should follow `details[open]` without replacing native toggle handlers. The real-browser regression is `tests/e2e/sprinkle-details.test.ts`; it checks visible content as well as `open`, since an attribute-only assertion misses misplaced summary content.
- Dips: `ui/dip.ts` hydrates assistant `shtml` code blocks into sandboxed iframes as soon as a block's closing fence arrives; a block still streaming shows the "Pouring a dip…" card. Every re-render passes the previous instances to `hydrateDips`, which moves an unchanged dip across with `Element.moveBefore` (the iframe keeps its document) instead of remounting it. Without `moveBefore`, dips wait for the final render. `WcChatController.onMessageRendered` fires on every render while the old elements are still connected; `onMessageDisposed` fires only on removal. Minimal lick bridge; auto-height via ResizeObserver.

## Shell command authoring

### `.jsh` commands

- `.jsh` files are JavaScript shell scripts discovered from the shell's `$PATH` roots (default: `/workspace/skills`, `/workspace/.mcp/aliases`, `/workspace/bin`, `/shared/bin`; extend via `export PATH` or `~/.profile`); command name is the basename without `.jsh`. Two skills that ship the same basename are ranked (`.upskill` provenance, then newer `installed` timestamp, then first scan) and the collision is reported by `skill list`, `which`, and jsh registration — never a silent stale winner. `script-catalog.ts` shares discovery across `AlmostBashShell`, `which`, and other lookup paths. Scripts run in an async wrapper: prefer top-level `await`.
- Stdin (`process.stdin`) is fully buffered read-ahead (no streaming; latin1 strings, not `Buffer`s; `'error'` never fires) and one-shot: `read()`, events (`on('data')`→`'end'`→`'close'`, single chunk), and the async iterator share one `consumed` flag, so whichever drains first wins and the others see EOF. `read()` returns `null` (Node parity) when nothing was piped. On the events surface, `pause()` suppresses the deferred emission until `resume()` (the buffer stays drainable) and `process.exit(N)` from a handler exits with code `N`. `process.stdin.isTTY` is always `false`. Do not expose `stdin` as a top-level identifier (collides with user declarations).
- The `fs` shims (sync + async) also serve the stdio fd/device idioms: `readFileSync(0)` / `readFile(0)` / `'/dev/stdin'` return the FULL buffered stdin (encoding-aware; does NOT consume `process.stdin`'s one-shot flag — the buffer is separable), `writeFileSync`/`appendFileSync`/`writeFile` to fd `1`/`2` (or `/dev/stdout`/`/dev/stderr`) land on stdout/stderr, and `existsSync`/`accessSync`/`statSync` report the three stream devices as present (`isFile()` true pragmatically, `isCharacterDevice()` true, size 0). Wrong-direction stream ops and unknown numeric fds throw `EBADF`. Intercepted in `realm-fs-bridge.ts` BEFORE path resolution — no VFS entries involved (`/dev/null` stays a VFS-layer concern).
- `require('readline')` / `require('readline/promises')` resolve to a per-realm shim (`helpers/node-readline.ts`) over the buffered stdin: `createInterface({ input[, output, terminal] })` (or positional `(input, output)`) drains the input once (this DOES consume `process.stdin`, matching Node's flowing mode) and offers `'line'`/`'close'` events (one-hop deferred like the stdin shim), `for await` iteration, and `question()` (callback or Promise; echoes the query to `output` or the realm stdout, answers with the next unconsumed line, `''` at EOF). A final unterminated line is still emitted and CRLF is stripped, per Node.

### `.bsh` browser scripts

- `.bsh` files are JavaScript browser-navigation helpers that run in the **target browser page context** via CDP `Runtime.evaluate`. Access `document`, `window`, page globals — NOT `process`/`fs`/`exec()`. Filename controls hostname matching: `-.okta.com.bsh` → `*.okta.com`; `login.okta.com.bsh` → exact host match. Optional `// @match` directives in the first 10 lines narrow further. `BshWatchdog` uses `ScriptCatalog` for matching.
